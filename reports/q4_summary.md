# Q4 — Serving & scale analysis: results

Generated by `src/serving/q4_report.py` from `reports/q4_*.json`. Reproduce everything with `make q4`.

## Setup

- **System served:** the full two-stage pipeline. Stage 1 = BM25 top-80 ∪ FAISS top-100 (A1 embeddings) ∪ train-popularity top-20, deduplicated to ≤200 candidates from the circulating pool. Stage 2 = Q3 popularity-aware NRMS (EB-NeRD adds freshness) → top-10.
- **Hardware:** Apple M4 (4 performance + 6 efficiency cores, 16.0 GB RAM), CPU, **1 thread** (PyTorch, FAISS/OpenMP and BLAS pinned; torch 2.13.0, faiss 1.15.0).
- **Protocol:** start-up (indexes, model, every article's NRMS vector) is loaded once and never timed; requests replay real (user, timestamp) pairs from the test split, one at a time.
- **Two stage-1 modes, identical output (tested):** `as_is` calls the existing batch-evaluation functions per request; `serving` computes the parts that never change between requests once at start-up.

## Q4.4 Scale: 10× measured on a synthetic catalogue

Articles copied 10×, each copy's vector perturbed (σ = 0.01) and re-normalised; BM25 rows, NRMS article vectors, pool and click events replicated. 1,000 real test users replayed against 1× and 10×. Index builds used every core; every timed search used 1 thread. FAISS ran in a child process without PyTorch (duplicate OpenMP runtimes abort multi-threaded FAISS when PyTorch is loaded). 1× totals are calibrated to Phase 3's measured mean.

| p99 ms, 1× → 10× | MIND-small (65,238 → 652,380 articles) | EB-NeRD small (20,738 → 207,380 articles) |
|---|---|---|
| BM25 (serving) | 0.90 → 2.92 | 2.09 → 3.72 |
| FAISS flat over pool (served) | 0.15 → 1.43 | 0.17 → 1.21 |

## Caveats

- Laptop, not a server: Apple M4, 1 thread; macOS may schedule on efficiency cores, and numpy's BLAS (Accelerate) offloads to the AMX coprocessor, so per-core figures are indicative, not cloud-vCPU exact.
- Only the in-process pipeline is timed: no network, request parsing, or remote profile/click-counter stores.
- The circulating candidate pool is built from the whole test period (inherited from Q2's retriever): slightly optimistic for recall, no effect on latency or memory.
- Synthetic 10x catalogue = perturbed copies of real articles: HNSW recall is measured on a clustered set.
- BM25 rows are copied, so vocabulary and term statistics do not grow as a real 10x catalogue's would.
- Users x10 is a linear memory extrapolation; profile lookup is O(1).
- Index builds used every core; every timed search used 1 thread.
